## 剑一：ConStory-Bench（ACL 2026，arXiv 2603.05890）—— 写侧一致性

**基准结构**（已核实）：
- 2000 prompts、4 种任务类型，数据集在 HuggingFace（jayden8888/ConStory-Bench）
- 评测全自动：`constory.generate`（OpenAI 兼容，支持自定义 api-base → 可直接用我们的 api.u-claw.org.cn/v1）→ `constory.judge`（ConStory-Checker，5 类 19 子类）→ `constory.metrics`（CED）
- 在线榜单：picrew.github.io/constory-bench.github.io/leadboard/

**行动路径**：
1. **先行 pilot（本周可跑）**：clone 仓库 → 装依赖 → 取 20 条 prompts → 用 a0 裸模型臂生成（我们的 hermes 通道）→ judge + metrics。目的：打通管线、拿到 CED 基线，进他们的榜单。
2. **a3 本象臂适配（里程碑）**：把 context-compiler 适配到 ConStory-Bench 的 prompt 格式（4 种任务类型的 world spec 建模）。这是真正的亮剑：状态机臂 vs 裸模型，上他们的尺子量。
3. **互认**：等 issue #1 回复——争取 CED 精确定义（归一化窗口/子类权重/判分者分歧消解），把我们的 W1 判分器与 ConStory-Checker 对齐，避免"近亲变体"碎片化对比。
4. **百万字语料 offer**：world-spec-first 构造法（ground truth by construction），30k→1M 字 CC0 语料，按他们的规范建。

**风险提示**：ConStory-Bench 论文发现"多步 agent 系统一致性反而更差"。a3 上他们的榜**可能不赢**——这不丢人，这正是"外部检查"的意义；诚实结果本身就是项目的差异化叙事（参考 README 撤稿先例的舆论效果）。

## 附录 A：a3 本象臂适配 ConStory 设计（2026-08-06）

**目标**：让本象状态机臂跑 ConStory-Bench 的 2000 prompts，上他们的在线榜单，与裸模型/主流模型同台比 CED。

**ConStory prompt 四类**（已实测 prompts.parquet）：
- generation（751）/ continuation（432）/ expansion（422）/ completion（395），英文为主，每条 prompt 内嵌叙事要求（指定场景、闪回、角色动机等）

**适配思路**（沿用 ShadowBench-W 的 context-compiler + commit-compiler 模式）：
1. **输入侧编译**：把 prompt 解析为初始世界规格——角色对象（名字/关系/动机）、地点、时间线、prompt 要求的必现元素（如"dachshund 抓老鼠证明自己"→ 目标状态 + 禁入区）
2. **分块写作**：story 按 ~2k 词分块，每块前把当前状态投影进上下文（视觉地图 + 对象图 + 必现元素检查）
3. **输出侧提交**：每块结尾强制提交语义事务（谁知道了什么、谁在哪、时间推进），校验约束（禁入区/必现元素/角色一致性）后写下一块
4. **ConStory 判分对接**：产出 standard generated_story parquet 列 → 走同一套 constory.judge/metrics，无任何特殊通道

**与 ShadowBench-W 的分工**：ShadowBench-W 考"状态能否被正确持久化回写"（W3，内部考题）；ConStory 考"长文一致性错误密度"（CED，外部考题）。同一套状态机，两个尺子。

**预期**：论文发现多步 agent 系统一致性更差——本象臂可能不赢。但即使 CED 持平，只要「隐藏状态追踪」维度有可展示数据，榜单叙事就成立。诚实结果 > 输赢。

**落地位置**：新臂 arms/ 下（如 a4-constory），不动现有 a0/a3；prompt 解析器先手工规则后 LLM 辅助。

## 附录 B：ConStory pilot 实测结果（2026-08-06，最终版 n=52）

**环境**：Picrew/ConStory-Bench 官方仓库，本地 venv 跑官方管线；生成 deepseek-v4-flash（hermes 通道 api.u-claw.org.cn/v1，max_tokens 16384），判分 qwen-plus（换模型避免自评偏倚）。

**最终结果**（prompts 0-60 子集，52 条完成故事，289,200 词，平均 5,561 词/篇）：
- **CED = 0.52**（15 个一致性错误）
- 按类别：timeline_plot 6（弃置情节线）、factual_detail 4（命名混淆）+ 3（数值不符）、characterization 2（记忆矛盾）
- 按任务：expansion 0.24（n=14）< completion 0.26（n=17）< generation 0.30（n=6）< **continuation 1.03（n=15，10/15 的错误都在这）**
- 对照他们榜单（22 个模型）：0.52 落在 Claude-Sonnet-4.5（0.520）和 GLM-4.6（0.528）之间，压过 DeepSeek-V3.2-Exp（0.541）——中游偏上，方向性信号

**判分器可信度对照实验**：往故事注入两处明显矛盾 → ConStory-Checker 抓到并精确引用原文。注意子类归类有偏差（注入落在 narrative_style 而非 characterization/factual）。

**运行教训（放大 n 必读）**：
1. generate 的 asyncio 收尾会挂死（完成后不退出）——脚本已用 `timeout` 包裹，以 parquet 落盘为准；墙钟 timeout 3600 会误杀内存未落盘批次（批 2 两次被掐，各丢 ~5-10 条内存成果），建议墙钟 ≥5400 且每批结束后检查 parquet 行数决定是否续跑
2. 批内单请求可能长时间无返回（同一批 4 条里常卡 1 条），aiohttp 600s 超时未生效；重试 3 次 ×10 分钟 = 单条最多 ~30 分钟。顽固 prompt（本次 22/24/28/31/33 五条）稳定超时，resume 后仍失败——建议对失败 id 单独降并发/降 max_tokens 重试，别混在大批里
3. judge 输出目录默认 `output/` 不是 `evaluations/`，metrics 找的是后者——脚本已加 `--output-dir evaluations`
4. **judge CSV 是周期保存的**：judge 进程未退出前读 CSV 会读到部分数据（我因此把批 3 的 0.79 误读成 0.26）——分析前先确认无 judge 进程、mtime 稳定
5. 60 条全量成本：~3 小时墙钟 + 约 ¥30-50（含失败重试），成本可控

**产出文件**（本地 constory-bench/）：

- evaluations/judge_deepseek-v4-flash_*.csv（三批判分）+ merged_n56_final.csv（合并 52 条）
