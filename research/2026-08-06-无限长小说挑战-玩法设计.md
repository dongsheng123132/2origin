# 无限长小说挑战 · 玩法设计（2026-08-06）

> 用户问：「是弄一个创作台还是怎么玩？」——答：**不做创作台，做直播式公开跑**。

## 为什么不是「创作台」

创作台 = 产品（注册/登录/付费/编辑界面），重、慢、冷启动难。
直播式公开跑 = 事件（一个公开仓库 + 每天自动长一章），轻、快、自带传播。

区别一句话：创作台是「让人来用工具」，公开跑是「让人来看世界长」。
后者天然适合传播——读者追的不是工具，是**一个正在发生的、不会断更的连载**。

## 玩法（MVP，本周可上线）

```
公开 GitHub 仓库：infinite-novel/月落渡口
├── world/            世界规格（canon/伏笔/时间线/禁区）
├── narrative/chapters/chNN.txt   每章正文
├── public/index.md   连载索引（章/字数/日期/链接）
├── public/state-chNN.md   每章世界快照（人物/物品/伏笔图谱）
├── provenance/       事务证据链（谁在什么时候改了什么）
└── README.md         规则 + 里程碑 + 加入方式
```

**自动连载**（cron 每日）：
```bash
# 续写一章（模型 → 事务 → 五道门禁 → 落盘 → 快照 → 索引）
npm run story:serial -- <pkg.origin> --provider hermes --title 月落渡口
git add -A && git commit -m "ch$(N): $(摘要)"
git push
```
每章一个 commit = 公开的时间戳证据链。「公开跑」三个字全部落在这上面。

**里程碑**（传播节点）：
- 第 30 章 / 10 万字：发首篇博客（hequbing.com），宣布挑战开始
- 第 100 章 / 30 万字：X/公众号/知乎同步，贴世界快照截图（状态可视化是卖点）
- 第 300 章 / 100 万字：「AI 以事务机制续写、状态全程可验证」的百万字达成
- 此后：向吉尼斯/纪录类媒体投稿（「世界最长 AI 生成小说」定语可争）

**读者互动**（轻量，不加产品）：
- GitHub Issues 投票下一章走向（模型提示词里带上得票最高的选项）
- 读者提伏笔：issue 提「希望埋一个伏笔：…」，审核后进 world 的 foreshadowing
- 断更透明：每天一章，缺更日公开原因（这是「直播」的诚实性，也是信任资产）

## 为什么这套玩法成立（对用户三个问题的回应）

1. **公开 = 最大的保护**：git 历史 + provenance 双重时间戳，「谁先定义考题/谁先跑百万字」
   查得出来；闭源藏着的对手 2027 年发同款时，你的 2026 年连载已经是公开档案。
2. **跑得快 = 生态位占领**：ShadowBench-W 已确认「状态回写正确性全球无榜单」——
   公开跑连载 = 在没人定义过的地方第一个定义，且每天都在更新证据。
3. **可验证 = 不可抄袭的卖点**：市面 AI 小说项目展示的是「文本」，
   本象展示的是「文本 + 世界状态 + 证据链」三件套——别人抄文本容易，抄这套机制要重写。

## 与「百万字小说网站」的关系

公开跑是**获客事件**，网站是**变现产品**。先跑起来（流量），
再在连载满 50 章时挂出创作台（订阅续写/自定义设定/付费追更）。
顺序不能反：先有观众，再有产品。
