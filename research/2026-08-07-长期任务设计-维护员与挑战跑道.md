# 长期任务设计：本象协议 + 2origin.org 的自动维护员

> 2026-08-07 · 状态：设计草案 · 用户决定「两个都要」
>
> 本文件回答：**把「维护本象协议和网站」变成一个长期运行的 Agent，该怎么落地。**
> 这也是本象协议自己的应用大挑战——长期记忆（跨天/跨月记住世界状态）+ 长期任务（每天自动干活）。

---

## 一、目标与定位

两条腿同时上（用户 2026-08-07 决定）：

| 跑道 | 角色 | 载体 | 特征 |
|---|---|---|---|
| **Mac Mini 私有维护员** | 我的每日执行者 | dsenmac-mini（16GB Apple Silicon，Tailscale 常驻，AC 供电 24h） | 完整 shell、本地模型通道、直接操作本地仓库 |
| **Cloudflare 公开跑道** | 对外挑战赛 | Durable Objects + Agents SDK | 同平台可复现、全球可接入、闲置零成本 |

共同目标：**让「本象协议 + 2origin.org 网站」被一个长期 Agent 持续维护**——
每天读新论文/issue/PR、提交改进、更新文档、跑测试、写日报、必要时发版。
这不是「放任 AI 自己写」，而是**设计一个可验证、可复现、可比较的长期智能体实验**
（参考 ChatGPT 2026-08-07 会话里的 Long-running Agent Challenge 构想）。

## 二、为什么这是本象协议自己的考试

本象协议的核心主张是「状态追踪」：
> 需要跨整体累积、且从不在任何一段文字里被陈述的状态，只有状态机答得出来。

一个长期维护员每天面对的正是这种状态：
- 「今天之前，哪些决策已经定过、为什么」（跨天累积，不写在任何一份文档里）
- 「哪些待办还开着、哪个 PR 卡在哪一步」
- 「网站上的数字和仓库里的实验结果是否一致」（公开面核对）

如果本象协议连「自己」都维护不好——连自己的世界状态都记不住——
那对外宣称的「AI 时代的持久对象层」就只是口号。**这是 eat your own dog food 的最硬版本。**

### 3.3 每日维护循环（核心设计）

维护员的「一天」是一个由**调度器**触发的循环，每步都过本象协议的事务校验：

```text
每天 09:00（或 cron）→ 调度器唤醒维护员
  ├─ 1. 拉最新仓库 + 读 project.origin/ 世界状态（origin_status）
  ├─ 2. 对外部输入做一日清单：
  │     · GitHub：新 issue / PR / star / fork
  │     · 外部：新论文、新 benchmark、竞品动态
  │     · 自己仓库：测试失败、待办到期、公开面数字待核对
  ├─ 3. 选今天要做的 1 件实事（有验收标准；允许「今天没有需要改的」）
  ├─ 4. 执行：改代码/改文档/跑测试
  ├─ 5. 通过本象 commit（留证据链，违规零写入）
  ├─ 6. 跑全仓 verify
  ├─ 7. 更新 world state（今日决策/待办/事实，都进 project.origin/）
  └─ 8. 写日报（当日进展 + 数字 + 明天待办），发到网站或 GitHub
```

**关键规则**：
- **每天必须有客观输入**（新 issue、新论文、测试失败），不靠 agent 自己想象
- **允许「今天不改」**——这是合理结果，接近真实工程环境
- **每步留痕**——事务 + 证据链，`git log` 就是日报的证据
- **公开面数字核对**（task:public-surface-accuracy-check）是每日必做项之一

### 3.4 调度器

最简单可靠的调度器就是 **cron + 一条 bash 脚本**，不引第三方：

```bash
# ~/work/2origin/scripts/maintain-daily.sh
#!/bin/bash
cd ~/work/2origin
git pull --ff-only
# 调 claude 做每日维护（任务文件模式，长提示词写 task.md）
claude -p "$(cat scripts/tasks/daily-maintain.md)" \
  --allowedTools "Bash(git:*),Read,Write,Edit" \
  > logs/daily-$(date +%F).log 2>&1
```

crontab：`0 9 * * * ~/work/2origin/scripts/maintain-daily.sh`

## 四、Cloudflare 公开跑道

### 4.1 为什么是 Cloudflare

2026-06 调研确认（见 `research/2026-08-07-cloudflare-long-run.md`）：
- **Durable Objects** 的 actor 模型：Agent「持续存在、间歇运行」，闲置休眠零成本，消息/闹钟唤醒
- **持久状态**：`this.state` + SQLite 每次 `setState` 落盘，重启/崩溃都存活——天然匹配本象包
- **Fibers**：长任务中途被杀可 checkpoint 恢复——天然匹配本象事务语义
- **成本模型**：10,000 个 agent 各 1% 活跃只需 ~100 实例，按实际用量付费

### 4.2 公开挑战赛形态

```
long-agent-challenge（独立仓库）
  ├─ challenge rules（规则：每个 agent 接同一份世界规格）
  ├─ 评测框架（每天自动跑：状态准确率 / drift-rate / 完成度）
  ├─ 三个参赛位：A0 裸模型 / A1 向量RAG / A3 本象
  └─ leaderboard（每天更新：谁坚持下来了，谁挂了）
```

**与 ChatGPT 会话里「Long-running Agent Challenge」的区别**：不做「比谁写代码快」，
而是**比谁在跨天任务里状态一致性衰减得慢**——这正是本象协议的主张落点。

### 4.3 门槛与诚实边界

- Cloudflare computer 是 **PREVIEW**（API 不稳定、设计会变），适合原型，不适合生产
- 出站网络受限、模型调用从 Workers 需配 API key
- 本象协议仓库本身就是「本象 vs 裸模型 vs RAG」三臂对照的天然实验场
  （`benchmark/shadowbench-w/arms/` 的抽象可复用）

## 五、落地顺序（建议）

```text
Phase 1（本周）  网站上线（Vercel + 2origin.org）→ 长期维护员的「家」先立起来
Phase 2（本周）  Mac Mini 装 claude + 拉仓库 → 手工跑一次完整维护循环（冒烟）
Phase 3（下周）  cron 自动化 → 连续跑 7 天 → 修调度/脚本问题
Phase 4（30 天） 跑满 30 天 → 写「30 天长期维护员」报告 → 对外公开（这就是挑战赛的第一个参赛者）
Phase 5（远期）  Cloudflare 公开跑道：把 30 天报告 + 三臂数据变成 leaderboard
```

## 六、验收标准

1. **维护员连续跑 N 天**（先 7，后 30），每天有客观输入、有输出（改或明确不改）
2. **每步留痕**：project.origin/ 世界状态持续演化，`git log` 可复核
3. **公开面零失准**：网站数字 = 仓库数字（task:public-surface-accuracy-check 每日过）
4. **本象协议自己的 W3 不衰减**：维护员自己的世界状态 drift-rate 归零
5. **对外可复现**：任何人 clone 仓库 + 读文档就能理解维护员在干什么

---

> **一句话**：长期任务不是「放一个 AI 天天跑」，而是「把『维护本象协议』本身变成
> 本象协议的第一个长期应用案例」——它维护的既是协议，也是自己的世界状态。
