# benchmark/context-lod · 上下文编译器的预算行为

> **一句话结论：预算不是一个上限，是两个悬崖。**
> 基线在有 task 时饿死（平均只用掉 13% 预算，可寻址 24%），在无 task 时撑爆
> （宿主退回 renderAll，约束被截尾切光，规则存活 0/6）。中间没有任何档位。
>
> 复现：`node benchmark/context-lod/bench.mjs`（确定性，不调模型，秒级）

## 为什么这一轮不调模型

被测的命题是**投影本身的性质**——同一预算下，模型能看见世界的多少、规则还在不在。
这是编译器的纯函数属性；调模型只会把它埋进采样噪声，还要花钱。
模型侧的下游效应（违反数、事务通过率）归 ShadowBench-W，那是另一场实验。

## 三个臂

| 臂 | 是什么 |
|---|---|
| **A · v0.1** | 基线：相关性二值选取 + 超预算不处理。本臂如实模拟上游按预算硬截尾——只测编译器输出而不测被截之后，等于假装超预算没有代价 |
| **A′ · 宿主兜底** | 无 task 时 MCP 走的 `renderAll` 全量倾倒（`adapters/memory/mcp-server.mjs` 旧版），基线唯一真正溢出的路径 |
| **B · v0.2** | 相机 + 细节层次（LOD）+ 预算斜坡 |

## 四个指标

| 指标 | 定义 |
|---|---|
| 预算利用率 | 实际字符 / 预算。低 = 浪费，>1 = 溢出（会被上游截） |
| 可寻址对象 | 完整 ID 出现在文本里的对象数 / 世界对象总数。**模型只能引用它见过的 ID** |
| 规则存活 | enforceable 约束 + 禁区，逐条是否完整出现。这一项是 0/1 的生死题 |
| 焦点保真 | 任务点名对象的状态字段，有多少条真的进了上下文 |

## 这场实验烧出来的线上缺陷

`renderAll` 把约束排在全部对象**之后**，而 129 个对象在任何预算档下都排得满满当当。
于是按预算截尾时，**6 条「违反即拒绝提交」的约束在 1500/3000/6000/12000 四档下全部被切掉**
——恰恰是会话恢复这条最需要规则的路径上，模型一次都没见过规则。

已修：`origin_state` 不再退回 renderAll，改由编译器的预算斜坡接管（约束作为不可降级的
固定开销先扣，剩下的预算从「最近被改动过的对象」开始由近及远买细节，够不到的对象仍留
一行 `id（名）` 保持可寻址）。回归保护落在 `adapters/memory/e2e.mjs`。

## 降级阶梯（project.origin · 无 task · 129 对象）

约束本身要 275 字符。预算装不下它时如实报 `overBudget`，而不是偷偷切规则：

| 预算 | 输出 | 超预算 | full/key/id | 丢弃 | 约束在 |
|---:|---:|---|---|---:|---|
| 0 / 50 / 200 | 275 | ⚠️ 是 | 0/0/0 | 129 | ✅ |
| 400 | 398 | 否 | 0/1/3 | 125 | ✅ |
| 1000 | 990 | 否 | 0/1/24 | 104 | ✅ |
| 6000 | 5990 | 否 | 1/94/34 | 0 | ✅ |

**优先级是硬的：规则 > 焦点细节 > 邻居细节 > 背景可寻址。** 丢弃永远显式记进
`ctx.dropped` 并在正文里留一行「另有 N 个对象未列出」——静默丢弃是上下文编译器
最容易犯、也最难查的错。

## 方言怎么接进来

预算斜坡是领域无关的，但「给模型看什么」不是。核心用 `project` 着色器把两者分开：

```js
compileContext({ origin, task, budget, project: { cast, render, group, fixed } })
```

叙事域的实例见 `arms/a3-benxiang/context-compiler.mjs` 的 `narrativeShader`——
主角 + 同地者 + 持有者进画面，人物给 location/伤/生死/knows，物品给 holder/used，
世界规则与地点词表进 `fixed`（不参与降级：地点 ID 被降档 = 模型开始编地名）。

该臂的合同是 **lod:false 时与旧 fork 实现逐字节相同**，`npm run test:a3-projection`
以 81 例（3 任务 × 3 状态 × 3 章次 × 无正文/短尾巴/29 万字全量尾巴）守住。开 `lod:true` 才启用斜坡：
同样 1200 预算，关 = 1284 字符（溢出），开 = 1197 字符（守住），世界规则一条不少。

## 阴性结果：ShadowBench-W 上跑 LOD 会花钱测到零

A4 臂（A3 + `lod:true`）已建好并跑通，但**不建议在 ShadowBench-W 现有世界上花钱跑**。
理由是先测出来的，不是事后找的：

```
node benchmark/context-lod/engagement-probe.mjs        # 触发阈值探针
```

| | ShadowBench-W 世界 | project.origin |
|---|---|---|
| 可渲染对象 | 13（8 人物 + 6 物品，去重后） | 129 |
| 满档投影成本 | **1527 字符** | 37998 字符 |
| 实验预算 | **6000** | 6000 |
| 斜坡触发 | ❌ 恒不触发（6000 ≫ 1527） | ✅ 每一档都触发 |

stub 实跑佐证：A4 的 `lodStats` = `{frames:5, degraded:0, dropped:0}`，
两臂输入 token **完全相同（25358）**。斜坡一次都没动手。

扫描下来，这个世界要到预算 **1600 以下**斜坡才开始降档、900 以下才开始丢对象——
而那是没人会用的运行点。**在这里跑 A3 vs A4，测的是采样噪声，不是机制**，
而 results-log 反复强调单次运行的方差大到能翻转结论。这种数字比没有数字更坏。

要真正测 LOD，需要的是**状态段撑爆预算的世界**（满档成本 > 预算），
ShadowBench-W 的 S 与 M 用的是同一个 `world/spec.origin`，换任务不换世界，都不满足。

> 这条阴性结论在跑之前就写进了 `arms/a4-lod/index.mjs` 的文件头，跑完照录，
> 免得事后从一堆数字里挑一个好看的解释。

## 模型侧：已测，见 state-recall/

`project.origin` 上跑了真实模型（deepseek-v4-pro，24 题 × 3 轮）：

| 臂 | 正确率 | 幻觉率 |
|---|---|---|
| 兜底倾倒 + 硬截 | 37.5% | 0% |
| v0.1 二值选取 | 0% | 0% |
| **v0.2 预算斜坡** | **62.5%** | 0% |

**正确率 ≡ 可见率，三个臂严丝合缝**——模型在且仅在值可见时答对，没有一次编造。
所以「可见率」是「正确率」的免费预测器：确定性可算，投影改动先用它筛，再花钱验。

跑之前写下的主假设（LOD 把编造换成诚实弃权）**没被证实**：三个臂幻觉率都是 0%，
没有编造可供转化。详见 [`state-recall/README.md`](state-recall/README.md)，
含一个自己烧出来的度量错误（会让被测方案凭空好看 6 题）的留档。

## 没有验到的东西（如实记）

- **臂 A 的硬截断在这两个世界上没有触发**。基线在 `project.origin` 上的失败模式是
  饿死（1/129）而不是撑爆，所以「截尾先切掉禁区」这条只在臂 A′ 上验到，臂 A 上没有。
- **story 世界上 B 的增益很小**（可寻址 5/7 → 7/7，利用率 44% → 54%）。7 个对象的世界
  本来就装得下，LOD 没有用武之地。**世界越大，这套管线越值钱；小世界上它近乎白装。**
- **幻觉率没测到差异**：三个臂都是 0%，该模型完全遵守 UNKNOWN 指令，没有编造可供转化。
  换一个不那么听话的模型、或去掉提示词里「答错代价高于 UNKNOWN」那句，才可能拉开。
- **只测了一个模型、一类任务**（deepseek-v4-pro，短标量字段召回）。「正确率 ≡ 可见率」
  是本次运行的观察，不是定律。
- **A4 臂（ShadowBench-W 上的 LOD 臂）仍未跑真实模型**，理由见上方阴性结果：机制在那个
  世界上恒不触发。它建好了，等有合适世界时再用。
