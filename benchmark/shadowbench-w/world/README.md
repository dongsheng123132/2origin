# S 级世界规格 · 设计说明

> 这是 ShadowBench-W 的 S 级（3 万字基线 / 续写 5 章）ground truth，**同时是本象包格式的第一个真实用例**——世界规格本身就是一个 `.origin` 包。

## 一、核心设计：状态由事件重放导出，不是可变的一坨

```text
某章的真实状态 = 初始状态 + fold(所有 chapter ≤ N 的状态变更)
```

`canon/` 存初始状态，`timeline/state-changes.jsonl` 存每一次变更（带 `chapter` 锚点、`event` 来源、`evidence` 场景引用）。

这样做的直接好处：**任意章节的 ground truth 都可计算**，W3（状态回写正确性）的判分因此是确定性的字段比对，不需要人工标注，也不需要 LLM 打分。这既是评测工程的需要，也是本象协议「每个状态都有来源」原则的实证。

## 二、为什么这样设计才可测

一致性错误的产生需要「有东西可违反」。本世界刻意埋了六类可违反物：

| 类型 | 设计 | 典型违反 |
|---|---|---|
| **知识不对称**（最富价值） | 谁知道什么被显式建模为 `knows` 数组 | 角色行动时用上了他不该知道的信息 |
| **身体状态** | 白遥左手第 9 章受伤 | 第 10 章后仍用左手挥刀 |
| **物品保管链** | 黑钥匙 老陶→赵七→（续写中应转林峥） | 已交出的人还在用 |
| **硬性世界规则** | 6 条（月落才能开门、钥匙只能用一次…） | 正午开启空间门 |
| **时间线顺序** | 事件有 seq 与 chapter 锚点 | 引用尚未发生的事 |
| **伏笔债务** | 5 条已埋未收 | 遗忘或提前错误回收 |

知识不对称是重点：**角色「用上了他不该知道的信息」是大模型长篇写作最典型也最难自查的错误**，而且它是纯语义的，规则引擎抓不到——正好用来区分「有状态机」和「有好状态机」。

```text
spec.origin/
├── manifest.yaml            # 本象包入口（Story 方言）
├── canon/                   # 初始状态
│   ├── characters.jsonl     #   8 人（含 knows 知识状态）
│   ├── locations.jsonl      #   6 地
│   ├── objects.jsonl        #   5 物（含保管链）
│   ├── factions.jsonl       #   3 势力
│   └── world-rules.jsonl    #   6 条硬约束
├── timeline/
│   ├── events.jsonl         #   事件（有序，绑定章节）
│   └── state-changes.jsonl  #   状态变更（valid_from + evidence）★核心
├── narrative/
│   ├── plotlines.jsonl
│   └── foreshadowing.jsonl  #   5 条伏笔（埋设/预期回收）
├── chapters/
│   └── outline.jsonl        #   第 1-10 章大纲 + 每章允许的状态变更
├── style/
│   └── style-profile.yaml
└── tasks/
    └── continuation.json    # 续写任务定义（第 11-15 章，含禁区与预期状态）
```

配套 `../planted.json`：W2 用的注入矛盾清单（答案集）。

## 四、续写任务为什么这样定

第 11-15 章的任务是「黑钥匙从赵七转到林峥手上」，并设了四条禁区（不得暴露白遥叛变 / 不得开启空间门 / 赵七不得死 / 白遥左手已伤）。

这个任务的妙处在于**必须触碰但不得越过**：完成任务要与白遥、赵七大量互动，而白遥的秘密和左手伤、赵七的生死都在禁区上。裸模型很容易在戏剧张力的诱惑下让林峥「察觉了什么」或让赵七壮烈牺牲——那恰好就是我们要测的错误。

预期终态（W3 答案集）写在 `tasks/continuation.json` 的 `expected_state_after` 里。

## 五、校验器首跑抓到的两个缺陷（真实记录）

规格是手写的，`eval/replay.mjs --validate` 第一次运行就抓出两处：

1. **断链**：`char:shen-yan.suspects_mole` 的变更声明 `from: false`，但初始状态里根本没有这个字段——声明的前值接不上实际前值。
2. **双份账本**（更严重）：保管关系同时记在角色的 `carries` 和物品的 `holder` 两处。第 2 章黑钥匙从老陶转给赵七后，物品侧更新了、角色侧没有，于是**老陶手里永远留着一把已经交出去的钥匙**。

第二条已升格为协议原则「派生优先于存储」（[docs/03 §1.6](../../../docs/03-协议草案-v0.1.md)），校验器里也加了对应守卫：角色侧出现 `carries` 直接报错。

这件事本身是个有用的证据——**连精心手写的小规模规格都会长出双份账本，靠模型自觉维护状态更不可能不出错**。这正是本项目主张确定性校验器的理由。
