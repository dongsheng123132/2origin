# 03 · 协议草案 v0.1

> 状态：草案（Draft）。本文档定义本象包（`.origin/`）的最小结构、Origin IR 六部分核心、三层上下文投影和语义事务格式。JSON Schema 草稿见 [`spec/schemas/`](../spec/schemas/)。

## 一、设计原则

1. **联合式元格式，不发明大二进制。** 不强行替代 USD、DOCX、Arrow、HDF5、图片和视频，而是在其上建立统一身份、关系、投影、动作、来源、验证。参考 OCI 镜像规范的思路：manifest + 可独立寻址的分层载荷，而不是一个无法扩展的巨大数据块。
2. **通用外壳 + 领域方言。** 通用外壳只定义生命周期和最小结构；Office、CAD、Story、Memory、Chart 各自扩展 Schema。它们不共享内部对象，只共享同一套动作：`inspect / render / query / act / diff / validate / commit / rollback`。
3. **原文是本源，摘要是投影。** 精确正文、事件和人工确认的设定是 source of truth；摘要可随时重建，无权覆盖本源。
4. **推断与事实分离。** AI 推测必须显式标注 `status: inference` + 置信度 + 证据引用，不能自动写成设定。
5. **每个状态都有来源。** 任何状态字段都能追溯到产生它的事件和证据。
6. **派生优先于存储。** 同一事实只许有一处真相，能推导出来的绝不另存一份。
   > 实证：ShadowBench-W 的世界规格首次跑校验器就被抓出此类缺陷——保管关系同时记在角色的 `carries` 和物品的 `holder` 两处，物品转手后两边即刻失配（前持有人手里还留着一把已交出的钥匙）。修法是删掉角色侧、由物品侧派生。**双份账本是状态腐坏的头号来源，协议层面必须禁止。**
7. **ID 必须自带归一化层。** 基于 ID 的协议若要求模型精确复现命名空间前缀，实践中必然大面积失败。
   > 实证：首次真实实验中，模型写出了合格正文与合理的状态变更，却因把 `char:zhao-qi` 写成 `zhao-qi`、`loc:dukou-teahouse` 写成 `dukou-teahouse`，被校验器判为「未知对象」，**5 章正文全部作废**。语义上毫无歧义的写法却被严格匹配拒之门外，这是接口刁难而非模型缺陷。两条修法缺一不可：①投影给模型时一律呈现完整 ID，不为「好读」剥前缀（模型会照抄你展示的形式）②提交侧做归一化解析（补前缀、别名消歧）。
8. **校验器必须区分「拒绝」与「完成」。** 一个把所有提交都拒掉的系统，在「错误率」指标上永远完美。
   > 实证：同一次实验里，本象臂因全被拒绝而产出零字，一致性错误率因此为 0.000，在只比错误率的判定下反而「赢」了裸模型。判定标准必须先要求任务完成，再比质量。
9. **管住状态管不住文字——两层必须分别把关。** 结构化状态正确，不自动带来生成内容正确。
   > 实证：本象臂出现过状态字段完全正确、正文却把关键物品写在错误人物手上的情况。提交编译器起初只校验状态变更声明，从不拿正文对照状态。把确定性规则接进门禁后，三次运行的错误数从 1/6/3 降为 0/0/0。
10. **系统可以拒绝，但不能沉默。** 拒绝必须留下可供人接手的产物。
   > 实证：门禁变严后，本象臂改为「写不合格就不给」，每轮丢掉 1-2 章——拿完整性换了正确性，真实使用中不可接受。改为「重试耗尽则收下错误最少的一稿并标记待人工复核」后，完成率恢复满额且质量仍优。这正是舟舱（人类确认层）在协议中的位置。

## 二、Origin IR 最小核心（六部分 + 来源）

最小本象不超过这六部分（YAML 示意）：

```yaml
artifact:
  id: sales-2026
  kind: dataset

payload:
  uri: ./sales.arrow          # 原生载荷，内容寻址

semantics:
  month: YearMonth
  revenue:
    type: Amount
    unit: CNY
  region: Region

relations:
  - revenue derived_from order_items

constraints:
  - revenue must_not_be_negative
  - projection must_disclose_truncation

projections:
  - engine: flint
    chart: Line Chart
    encoding: { x: month, y: revenue, color: region }

provenance:
  source: sales.xlsx
  imported_at: 2026-08-02
```

通用外壳的 JSON 骨架：

```json
{
  "artifact_id": "...",
  "type": "pptx",
  "nodes": [],
  "resources": [],
  "views": [],
  "provenance": [],
  "validations": [],
  "operations": []
}
```

## 三、本象包目录布局（`.origin/`）

```text
example.origin/
├── manifest.yaml            # 总入口：artifact 元信息 + 各部分索引
├── graph/                   # 结构本象（负责「懂」）
│   ├── objects.jsonl        #   对象（稳定 ID）
│   ├── relations.jsonl      #   关系
│   └── constraints.json     #   约束
├── payloads/                # 原生载荷（各领域自己的格式）
│   ├── building.usd
│   ├── finance.arrow
│   └── contract.docx
├── atlas/                   # 视觉总览（负责「找」，低 Token）
│   ├── overview.webp
│   ├── page-map.webp
│   └── diff-map.webp
├── exact/                   # 精确载荷（负责「准」，按需读取）
│   ├── text/
│   ├── tables/
│   ├── formulas/
│   └── geometry/
├── behavior/                # 行为与动作（对接影核）
│   ├── actions.json         #   允许执行的动作
│   └── validators.json      #   修改后必须通过的验证
├── projections/             # 面向人的输出投影（缓存视图）
│   ├── report.pdf
│   ├── overview.png
│   └── summary.md
├── provenance/              # 来源与历史
│   └── history.jsonl        #   事件日志（append-only）
└── evidence/                # 验证证据（对接叠象）
    └── validation.json
```

说明：

- `atlas / graph / exact` 三层对应三层上下文结构（见 [02-概念体系](02-概念体系.md) 第五节）
- 目录均可选，最小合法包 = `manifest.yaml` + 至少一个 `payloads/` 或 `graph/`
- 领域方言在此布局上扩展（如小说方言增加 `canon/ narrative/ timeline/ summaries/ style/`）

## 四、状态与推断的表示

状态字段必须带来源：

```json
{
  "object": "character:bai-yao",
  "field": "left_hand_injured",
  "value": true,
  "valid_from": "event:821-07",
  "evidence": "scene:821-04"
}
```

推断必须与事实分离：

```json
{
  "claim": "白遥可能希望保护林峥",
  "status": "inference",
  "confidence": 0.63,
  "evidence": ["scene:604-03", "scene:702-02"]
}
```

## 五、上下文投影请求（输入侧）

AI 不再「打开一个文件」，而是**从本象申请一个适合当前任务的投影**。一次请求包含：

```text
意图 + 本象对象引用 + 需要的投影类型 + 精度等级
    + 允许执行的动作 + 约束条件 + 验收证据要求
```

CLI 示意：

```bash
origin project company.origin \
  --target claude \
  --budget 1500 \
  --task "检查内容重复和版式异常"

origin fetch company.origin slide-17/chart-2 --exact
```

模型配置独立于本象（同一本象按不同模型的视觉 Token 算法与能力生成不同投影）：

```text
profiles/
├── claude.yaml
├── gemini.yaml
└── deepseek-ocr2.yaml
```

## 六、语义事务（输出侧，AI 的标准输出单元）

AI 不输出全文/终态，输出一个提交包：

```json
{
  "transaction_id": "tx-20260802-001",
  "operation": "append_scene",
  "target": "volume-07/chapter-823/scene-004",
  "depends_on": [
    "scene:volume-07/chapter-823/scene-003",
    "character:lin-zheng@state-822",
    "object:black-key"
  ],
  "content": { "format": "markdown", "text": "……本场景正文……" },
  "state_changes": [
    { "object": "character:lin-zheng", "field": "location",
      "from": "north-corridor", "to": "moon-platform" },
    { "object": "object:black-key", "field": "holder",
      "from": "zhao-qi", "to": "lin-zheng" }
  ],
  "foreshadowing": {
    "resolved": ["hook:missing-letter-702"],
    "created":  ["hook:bell-sound-823"]
  },
  "assertions": [
    "bai-yao-betrayal-remains-secret",
    "zhao-qi-remains-alive"
  ]
}
```

要点：

- **`depends_on`**：事务声明依赖的对象与状态版本，运行时据此检查冲突
- **`state_changes`**：显式的 from→to，可校验、可回滚
- **`assertions`**：AI 声明「本次修改不违反的边界」，由验证器复核
- **Flint 原则**：不要重新输出大型载荷，只引用对象 ID，由运行时绑定真实内容

提交后运行时执行：

```text
解析内容 → 检查依赖状态 → 检查约束 → 检查前后连接
→ 提交载荷 → 更新状态与关系图 → 更新摘要 → 重新生成投影 → 留存证据
```

对纯投影修改（不动源数据），事务退化为一个语义 Patch：

```yaml
patch:
  target: projections[0]
  set:
    chart: Grouped Bar Chart
```

## 七、统一动作面（所有方言必须实现）

```bash
origin inspect  <artifact>        # 总体信息与健康状况
origin render   <artifact>        # 生成视觉投影
origin query    <artifact> <expr> # 结构化查询（如 /slide[2]/shape[*]）
origin project  <artifact> --as … # 按需投影（pdf/semantic/…）
origin act      <artifact> --action …  # 通过影核执行动作
origin diff     <old> <new>       # 结构/语义/视觉差异
origin validate <artifact>        # 约束与完整性验证
origin commit   <transaction>     # 提交语义事务
```

暴露形态：CLI、MCP、REST API、SDK、舟舱审阅界面。

## 八、领域方言登记表（v0.1）

| 方言 | 本源是什么 | 生命周期示例 |
|---|---|---|
| Office | 页面、段落、单元格、幻灯片 | 打开→对象树→页面渲染→编辑→Diff→原生 Office 验证 |
| CAD | 几何、约束、参数、装配 | 打开→几何树→多视角渲染→改参数→几何检查→导出验证 |
| Archive (ZIP) | 容器与文件树 | 打开→文件树→安全扫描→递归解析→修改→重打包→完整性验证 |
| Web | DOM 与运行态 | 打开→DOM/A11y树→截图→操作→重放→像素与行为验证 |
| Media | 时间轴、镜头、字幕、音轨 | 打开→时间轴→编辑→预览→编码与内容验证 |
| Chart（Flint） | 数据 + 字段语义 + 图表意图 | 数据→语义类型→投影意图→编译→多后端图表 |
| Story | 正文、人物、时间线、伏笔、风格 | 上下文舱→AI 事务→连续性检查→提交→导出 EPUB/DOCX |
| Memory | 对话中的事实、决策、状态、待办 | 每轮→抽取变更→写入本象→检查点→旧对话退出上下文 |
