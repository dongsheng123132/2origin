# 04 · 架构设计

## 一、总体分层

```text
Word / CAD / Excel / 视频 / 网页 / 对话历史        （源世界）
                    ↓ 导入（Adapter）
              本象 IR（Origin IR）                 （对象层）
        对象 + 语义 + 关系 + 状态 + 约束 + 来源
                    ↓
              领域编译器（方言）                    （编译层）
      Flint(图表) / Office / CAD / Story / Memory
                    ↓
              Shadow Runtime                       （运行层）
        加载、计算、投影、执行动作的「虚拟机」
                    ↓
      图表 / PPT / PDF / DWG / GLTF / EPUB / 界面   （多影输出）
```

各项目在架构中的位置：

```text
影域 ShadowSpace ─ 一切发生在隔离空间内
本象 Origin ────── 对象层：世界是什么
影核 ActionParity  动作层：AI 想做什么、由谁执行
叠象 Redline ───── 证据层：改了什么、对不对、能否证明
舟舱 PodApp ────── 人类层：给人看什么、由人确认什么
```

## 二、双向编译器（核心机制）

```text
                 Context Compiler（输入侧）
本象 ─────────────────────────────────────→ AI
 ↑                                           │
 │                                           │
 └───────────────────────────────────────────┘
                 Commit Compiler（输出侧）
```

**输入侧（Context Compiler）负责：**

- 按任务选择相关信息（不是全量塞入）
- 生成视觉地图（atlas）
- 生成分层摘要
- 控制 Token 预算（按目标模型的视觉 Token 算法适配）
- 暴露可用动作

**输出侧（Commit Compiler）负责：**

- 解析 AI 提交的语义事务
- 检查数据结构与约束
- 检查影响范围与依赖状态
- 更新对象状态、关系图、摘要
- 保存版本证据
- 重新生成面向人的投影

这是从 Flint 得到验证的模式在全领域的推广：**AI 负责表达意图，编译器负责完成细节**（输入输出两个方向都成立）。

## 三、三级记忆结构（类比操作系统）

| 级 | 名称 | 内容 | 规模 | 类比 |
|---|---|---|---|---|
| L1 | 工作缓存 Context | 当前任务：当前页面、目标、约束 | 几十 KB | CPU 缓存/内存 |
| L2 | 项目本象 Project Origin | 架构、决策、TODO、状态、历史变化 | 几 MB | 数据库 |
| L3 | 原始档案 Archive | 所有聊天、文件、版本、实验 | TB 级 | 硬盘/冷存储 |

流动方向：

```text
Archive → 本象抽取 → Project Origin → Context Projection → 当前 AI 对话
```

对话侧的循环（Memory 方言）：

```text
每一轮聊天 → 识别新增信息 → 形成候选状态变更
→ 写入项目本象 → 生成新检查点 → 旧聊天退出活动上下文
```

下一次对话只加载：当前项目状态 + 相关历史决定 + 未解决问题 + 少量必要原始证据。完整聊天保存在 Archive，可精确调取，但不常驻上下文。

**理论依据**：上下文窗口再大也不等于有效利用——「Lost in the Middle」研究表明模型对长上下文中间区域的利用显著弱于两端；Anthropic 的上下文工程实践也把「持久保存重要信息 + 从活动上下文移除已处理内容」作为长期 Agent 的标准做法。无限扩窗不是根本答案，**管理**上下文才是。

## 四、与 RAG 的区别

```text
RAG：  文档 → 切片 → 向量 → 搜索几个片段 → 塞给 AI
本象：  文档 → 对象化 → 关系化 → 状态化 → 时间化 → 按任务投影
```

RAG 找到的片段不知道：为什么重要、和谁有关、状态是什么、是否已废弃、是否冲突。

一句话：**RAG 找相关文字，本象找相关世界状态。**

（GraphRAG 的实体关系 + 社区分层摘要已经证明「图结构 + 分层摘要 + 按需检索」优于全文塞入；本象在其上增加：精确原文、可修改对象、当前状态、写作事务、版本与验证。）

## 五、摘要漂移防线

常见长期记忆方案的致命伤：

```text
原文 → 摘要 → 摘要的摘要 → 更短摘要   （细节、动机、条件逐轮失真）
```

本象的四条防线（协议草案第一节原则的运行时体现）：

1. **原文和事实是本源**——精确正文、事件、人工确认的设定是 source of truth
2. **摘要只是可重建投影**——随时可从原文重新生成，无权覆盖本源
3. **推断与事实分开**——`status: inference` + 置信度 + 证据引用
4. **每个状态都有来源**——`valid_from` 事件 + `evidence` 引用，摘要出错也能追溯回原文

## 六、多渲染器路由与证据共识

不存在「绝对正确的万能渲染器」（LibreOffice 渲染 ≠ 微软 Office；服务器端自动化原生 Office 官方不支持且不稳定）。正确做法是**路由 + 共识**：

```text
同一个文件
 ├── 结构解析器
 ├── 开源渲染器
 ├── AI 语义解析器
 ├── 原生软件验证器（可选的 Windows 黄金节点）
 └── 截图与像素比较器
        ↓
  叠象汇总为可信度结果（不是一张 PNG，是带证据的结论）
```

生成物验收清单（叠象自动完成）：能否打开 / 结构是否损坏 / 页面是否溢出 / 字体是否缺失 / 公式是否错误 / 图片是否丢失 / 修改了哪些对象 / 视觉变化区域 / 语义变化 / 多渲染器是否一致。

## 七、视觉压缩的位置（能与不能）

「把文字放进图片省 Token」在本体系中的正确角色是**全局地图，不是唯一存储**：

- **能**：视觉总览提供空间关系、聚类、层级、模式，配合 Set-of-Mark 式对象编号，AI 低成本获得全局认识并精确引用对象（`看见 [A17] → 影核解析 → 执行 → 叠象验证`）
- **不能**：DeepSeek-OCR 的数据表明压缩超过 ~10 倍后精度快速下降；且「能读回文字 ≠ 能理解长距离关系」；过度压缩时模型靠语言猜测补全，产生「看起来读对了，实际是编的」

所以永远是三层配合：**图负责找，结构负责懂，原文负责准。**

## 八、UI/软件操作的接入（与影核的配合）

```text
AI 看见带编号的界面图 [A17]
        ↓
影核解析 A17 → 真实对象（DOM 节点 / 控件句柄）
        ↓
执行 click / input / drag
        ↓
叠象重新截图并验证
```

一张带对象编号的界面图，往往比几千行 DOM/Accessibility Tree 更容易让多模态模型建立全局理解——这正是「视觉总览 + 结构本象」双层的典型应用。
