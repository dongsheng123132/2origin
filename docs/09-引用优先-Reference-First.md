# 09 · 引用优先 · Reference-First

> **真值不搬运，只解析；解析必带新鲜度校验。**
>
> 本页是贯穿本象 / 影核 / 本境三协议与四层 stub 的通用原则。它不是某个协议的新增条款，
> 而是把三协议早已在用的同一个机制命名出来，让它变成新设计必须过的检查。
>
> 🌍 **[English](09-Reference-First.en.md)**

---

## 〇、一句话

**任何系统想在大尺度上保持不腐坏，办法只有一个：没有人搬运真相，所有人都只携带"找得到真相的最小地址"。**

- **不搬运**：真值只在真源处存一份，任何人需要它时拿的是**引用**（ID、名字、地址、指纹），不是真值的副本。
- **只解析**：引用在**使用时**才解到当时的真值，由解析器负责。
- **必校验**：解析的同时核对版本/水位/指纹——*content always matches the installed version*。

## 一、病根：拷贝注定漂移

把一份真值复制到第二个地方，就同时创造了**两份内容 + 一套同步义务**。同步是跟熵搏斗，必输：
你更新了 A 忘了 B，于是 A 和 B 都"正确"，却彼此不一致——而且没人知道该信谁。

文档里的版本号会过期，摘要会脱离正文，导出的图会脱离模型，双份账本会在转手后失配。
**所有这些病是同一个病：把真值搬运了第二份。** 引用优先不是去跟漂移斗争，而是**结构上让漂移不可能发生**——
第二份根本不存在，就无从失配。

> 实证（本象，双份账本）：保管关系同时记在角色的 `carries` 和物品的 `holder` 两处，
> 物品转手后两边即刻失配。修法是删掉角色侧、由物品侧派生——真值只留一处，另一处是引用/推导。
> 协议层面直接禁止双份账本。**双份账本是状态腐坏的头号来源。**

## 二、可信引用 5 属性

"引用"不是随便一个指针，而是**可信引用（Trusted Reference）**——同时满足五条才算数：

| # | 属性 | 含义 | 反例 |
|---|---|---|---|
| 1 | **极小** | 引用比被指物小几个数量级 | 把整本手册写进 stub |
| 2 | **稳定** | 被指物变，引用不变 | 引用里嵌了会变的内容 |
| 3 | **可解析** | 用时能经注册表/地址解到当前真值 | 只有引用，没有解析器 |
| 4 | **新鲜** | 解析带版本/水位/指纹校验 | 拿到真值，却不知道是哪一版 |
| 5 | **单一真源** | 真值只存一处，引用永不复制它 | 真值在 A、B 各存一份 |

缺 1 → 你搬的还是内容不是地址；缺 2 → 真值一变引用就废；缺 3 → 死链；
缺 4 → 用错版本；缺 5 → 双份账本。**五条全过，引用才可信。**

## 三、反例清单（日常最常犯）

| 反例 | 违反了哪条 |
|---|---|
| 在文档里硬编码版本号 | 1（搬了内容）4（必然过期） |
| 把投影当源文件改（改 PDF/截图/摘要） | 2、5（真源被动） |
| 双份账本（同一事实存两处） | 5 |
| 全量 schema/动作预载进上下文（40KB 塞给 agent） | 1（该按需取单条） |
| 文档与实现各写一遍规则 | 2、5（文档必然落后于实现） |
| 把可推导值另存一份 | 5（应派生） |

> 其中「双份账本」这条已在协议里被 `diagnose` 检测、但**尚未被一致性向量钉死**
> （conformance §五 缺口 #1）——按本页第六节的原则，它现在仍属于"实现自由"。
> 补向量是后续任务。

## 四、三协议与四 stub 都是它的实例

同一个机制在不同尺度上的表现——指什么、解析器是谁、新鲜度靠什么：

| 引用 | 指什么 | 解析器 | 新鲜度校验 | 尺度 |
|---|---|---|---|---|
| 本象对象 ID + `depends_on` | 对象状态 | origin CLI / MCP | `seq` 水位 | 内容 |
| 本象语义事务（Flint） | 大型载荷 | 提交编译器 | 校验/向量集版本 | 内容 |
| 影核动作名 | 动作 schema + 执行器 | open365 registry | 影核版本 | 动作 |
| 本境 fingerprint | 整台机器环境状态 | （未来环境 Git） | SHA256 分层哈希 | 环境 |
| uenv stub | 环境检查工作流 | `uenv doctor --agent` | `CARGO_PKG_VERSION` | 上手 |
| CLAUDE.md 指针 | 本机真值 | `uenv doctor` + `llms.txt` | 运行时不硬编码 | 上手 |

本象宣言的骨架——「保存本象，按需投影」「投影 ⇏ 唯一本象」「AI 交付事务而非终态」——
就是引用优先在"数字对象"尺度上的说法。四层 stub 体系（机器→项目→协议→动作）是它在"上手"尺度
的最小实例：stub 只指路，真值按需取、随版本走。

## 五、与既有原则的关系

引用优先不是新发明，是**把已经写进协议的几条原则认出是同一件事**：

- 设计原则 #6 **派生优先于存储**——"能推导出来的绝不另存一份"：引用优先在状态上的特例。
- 设计原则 #7 **ID 必须自带归一化层**——模型写不全 ID 就失败：引用必须能被稳定解析的体现。
- **Flint 原则**——"不要重新输出大型载荷，只引用对象 ID，由运行时绑定真实内容"：引用优先在输出侧。

这三条早就存在于协议里。引用优先把它们**泛化到一切设计决策**——不止状态、不止输出，
包括文档、schema、schema 预载、上手引导。

## 六、怎么用（日常自检四问）

新设计每引入一个状态/内容，先回答四问；**答不上任一问，就是设计没想清楚**：

> ① 谁是真源？（只许一处）
> ② 引用放哪？（别把真值复制到别处）
> ③ 解析器是谁？（用时怎么解到当前真值）
> ④ 新鲜度靠什么？（版本/水位/指纹）

落到日常：
- **设计评审**：`CONTRIBUTING.md` 硬规矩 #6 把四问写成提交前的自检。
- **决策记录**：本境 `DECISIONS.md` 每个待拍板决策都先过这一行站问句。
- **协议承诺**：引用优先只保证"可核对的部分"——能写成向量/校验的才算数，其余如实标注"未钉死"。
- **上手引导**：新工具/新协议诞生时自带一个 stub（极小、只指路、版本钉住），让陌生 agent 按需取真值。
