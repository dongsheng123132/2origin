# 07 · 开源与商业

## 一、策略总纲

**标准先开源，商业能力后置。** 目标是让本象协议成为事实标准（像 OCI 之于容器镜像），商业价值建立在标准之上的高保真、企业级、私有化能力，而不是把协议本身圈起来收费。

## 二、许可选择

| 内容 | 许可 | 理由 |
|---|---|---|
| 协议、Origin IR、核心运行时 | **Apache-2.0** | 比 MIT 多明确的专利授权条款，适合标准型基础设施 |
| 示例与简单 SDK | MIT | 最低采用门槛 |
| 测试数据 | CC0（自行生成）或 CC BY 4.0 | 避免版权纠纷，Benchmark 可自由复现 |
| 商业 Office / CAD 适配器 | 另行授权 | 见下方商业边界 |

正式 LICENSE 文件在首个可运行版本（Phase 2）发布时添加。

## 三、开源边界

适合开源（建立标准与生态）：

- 本象协议 / Origin IR 规范与 Schema
- 影核协议（动作定义规范）
- 叠象数据格式（差异/证据格式）
- Adapter SDK 与开源适配器
- 基础 CLI 与 MCP Server
- 通用验证规范、AI-Ready 文件标准
- ShadowBench 基准与测试数据

## 四、商业边界

可以商业化（标准之上的护城河）：

- **Windows 原生 Office 黄金验证节点**（真实 PowerPoint/Word/Excel 打开验证，高保真字体环境）
- 云端渲染集群、批量文档验收
- CAD 商业软件适配器
- 企业证据链（合规、审计、留痕）
- 安全沙箱与私有部署
- Artifact Benchmark 服务与「AI Ready」认证

与 U-King 现有产品线的结合：本象记忆增强 ClawX/U-Claw/Hermes 的长期记忆（装机即用的差异化能力）；Office 验收模块并入 Open365 场景；私有部署走 U-King 现有客户通道。

## 五、护城河分析

「把文字塞进图片省 Token」不是护城河——DeepSeek-OCR 已在做，模型厂商都会跟进。真正可积累的壁垒：

1. **可寻址的多维上下文**——图中每个对象都能定位回真实文件并可操作
2. **任务自适应编译**——按任务和 Token 预算生成不同视图，不是固定截图
3. **可执行**——AI 看见的对象可直接通过影核操作
4. **可验证**——每次操作都能重新渲染、比较、留证
5. **跨格式统一动作面**——PPT/Excel/网页/CAD 共享 observe/query/fetch/act/verify/commit

## 六、诚实边界（必读，防止宣传盖过工程判断）

本象协议**不是魔法**。对外表述和内部决策都必须承认：

1. **无法把任意 100 万字无损压缩成几千 Token** 并让模型同时理解每个细节。它做的是：不再要求模型一次理解全部内容；按任务选择相关内容；保留精确原文防止摘要失真；用结构关系找出潜在影响；用验证器减少连续性错误。**它管理上下文限制（像操作系统管理内存），不消灭上下文限制。**
2. **投影不可逆**——2D 恢复不出唯一 3D。所以必须始终保留本源，任何「从 PDF 猜回本象」的功能承诺都是错的。
3. **图片压缩是投影技术，不是存储方式**——压缩超过 ~10 倍精度快速下降；能读回文字不等于能理解长距离关系；过度压缩会产生「看起来读对了，实际是编的」。
4. **长距离关系理解仍是难题**——「某个微小细节是否影响 600 章后的情节」这类问题，系统仍可能漏掉。需要图谱检索 + 语义检索 + 依赖检查 + 定期全局扫描 + 人工确认重要设定的组合，且都不保证 100%。
5. **文学等创造性内容无法由确定性编译器生成**——编译器保证的是状态、时间线、约束和导出的一致性，正文创作仍靠模型。
6. **多渲染器共识给出的是可信度，不是绝对真值**——LibreOffice ≠ 微软 Office，永远存在渲染差异的灰区。

## 七、对外传播的标准口径

最高层：

> 过去，人类把世界压缩成文档交给计算机；未来，AI 将直接理解世界的本象，再为人类生成所需要的投影。

产品层：

> 一源万影：保存本象，按需投影。
> 图负责全局，结构负责关系，原文负责精确，影核负责执行，叠象负责证明。

技术层：

> 本象协议是面向 AI 工作的中间表示（AI 时代的 LLVM IR）：AI 不直接重造世界，只提交对世界的语义修改。

**禁用口径**（见 [02-概念体系](02-概念体系.md) 反面清单）：「支持 N 种格式」「无限压缩」「万能渲染器」（后者只可作为大众化的引子，须立即纠正为准确定位）。
