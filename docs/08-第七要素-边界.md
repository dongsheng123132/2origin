# 08 · 第七要素：边界

> **前六个要素回答「有什么」。第七个回答「没有什么」。**

## 一、它是被发现的，不是被设计的

本象原本声明六要素：对象、关系、载荷、状态、约束、来源。
但在落地四个方言与投影层的过程中，同一个动作被重复做了九次：

| 场合 | 做的事 |
|---|---|
| CAD | `id_basis=content` —— 稳定 ID 退化成内容哈希，写进包 |
| CAD | 块属性图纸不套「构件数=标注数」，并把选了哪套规则写进包 |
| 法律 | `closed_world` —— 库不完备时查不到只判 uncovered，不判 not-found |
| 法律 | 缺陷目录 D11/D12 —— 抓不到的两类写下来并**断言抓不到** |
| xlsx | 缺陷目录 D7–D10 —— 为压假阳性**主动放弃**的能力，写下来 |
| xlsx | `truncated_cells` —— 超出上限的必须报，悄悄少算等于假装全查了 |
| 投影 | `dropped` 是 `plan()` 的**主要产物**，不是可有可无的一项 |
| 一致性 | 覆盖缺口如实列出，补上之前「协议保证这几点」不成立 |
| 约束引擎 | 无机器判定的约束报 `unenforceable` 警告，而非静默跳过 |
| 实验 | Run #18 / #27 撤回自己已经发布的主张 |

**九次都在做同一件事：说出自己保证不了什么。**
那它就不是九个决定，是一条原则；而一条被九个互不相干的场合独立要求的原则，
不该继续以「代码注释 + README 段落 + stderr 警告」的形式存在。

## 二、为什么必须进包

因为消费方是 AI。**AI 不读 README，它读包。**

边界不进包，边界就不存在——下游会把一个已知有损的东西当作本体继续用。
而「投影的投影」正是本项目开篇要解决的问题：

> 一份不声明自己边界的表示，比一份坦白说自己很粗糙的表示更危险，
> 因为后者至少让人知道该去核对。

这条在法律方言上尤其重的原因：一份说不清自己边界的法律辅助工具，
会被当成「AI 审过了」——而法发〔2022〕33号 明确规定 AI 结果不得代替法官裁判。
**把边界写进包，是这条红线在技术上的落实方式，不是免责声明。**

## 三、五种边界

分类不是为了好看——**不同类型的补法完全不同**。

| 类型 | 含义 | 补法 | 例 |
|---|---|---|---|
| `degraded` | 本该有的能力退化了，仍可用但会失真 | 换更好的源 | R12 的 DXF 没有实体句柄，ID 退化为内容哈希 |
| `uncovered` | 参照数据不完备，判定范围小于声称范围 | 补数据 | 条文库只有 20 条 |
| `undetectable` | 这一类问题确定性检查抓不到 | 交给人，或换非确定性手段 | 整列用错了列（形状一致、数值合法） |
| `lossy` | 这一步已经丢掉了信息 | 回到上游取，不要从这里取 | 投影成 xlsx 时证据链带不走 |
| `unverified` | 有主张但尚未在真实条件下测过 | 去测 | 「假阳性为 0」出自自造夹具 |

## 四、声明必须可执行地具体

「本工具可能有误差」这种话等于没说：它不告诉下游该去核对什么，
也不告诉后来人该怎么补。所以 `checkLimits()` 强制四件事：

```js
limit(code, kind, scope, statement, remedy)
//    ↑     ↑     ↑      ↑          ↑
//    │     │     │      │          └ 怎么补（缺则告警：边界应当是待办，不是永久借口）
//    │     │     │      └ 这一条具体说的是什么
//    │     │     └ 管到哪（下游据此判断自己受不受影响）
//    │     └ 五种之一
//    └ 稳定标识（没有它就无法在下一版里说「这条已经补上了」）
```

**空清单也要出话。** `renderLimits([])` 返回的不是空字符串，而是：

> ⚠ 本包未声明任何边界。这不等于它没有边界，只等于没人写下来——
> 请勿据此认为它是无损、完备、已验证的。

## 五、怎么用

```bash
origin limits <包>                    # 接手陌生包时的第一个命令
origin limits <包> --scope 'cell:*'   # 只要与本次任务相关的
origin limits <包> --json             # 给 AI 吃
```

MCP 面上，`origin_limits` 的工具描述里明写「接手陌生包时第一个调用它」，
且 `origin_diagnose` 的返回值里带一句常驻提醒：

> 零 error 只等于「已启用的检查都过了」。哪些检查没启用、哪些已知抓不到，见 `origin_limits`。

这不是客套。法律方言真出过这事：解析失败时体检会报「零 error」，
而那个零的意思是「一条都没查」，不是「引用都合规」——所以才有了 `intake.mjs`。

## 六、诚实的边界（这一节自己也适用第七要素）

- **协议还没钉住它。** `compiler/limits.mjs` 与 `compiler/project.mjs` 一样，
  **没有一致性向量覆盖**。也就是说：另写一份实现，它可以合法地产出一个
  **不声明任何边界的包**而仍然「合规」。见
  [覆盖缺口](../spec/conformance/README.md)。
- **协议管不了「该声明却没声明」。** 校验器能查一条边界写得合不合格，
  查不了「这个方言明明有个坑却没写下来」。那要靠写方言的人诚实，
  以及变异检查这类外部手段。**第七要素降低的是「不知道自己不知道」，
  消灭不了「知道却不说」。**
