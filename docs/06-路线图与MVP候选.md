# 06 · 路线图与 MVP 候选

> 当前状态：**MVP 方向未定**。本文档给出三条候选路径的对比与决策标准。决策方式：先跑 ShadowBench 式小实验，用数据说话，不靠感觉拍板。

## 一、三条候选路径对比

| 维度 | ① 本象记忆 Shadow Memory | ② 100页PPT审阅 Demo | ③ 本象写作引擎 OriginWriter |
|---|---|---|---|
| **一句话** | MCP Server：聊天历史持续提交为项目世界状态，新会话秒恢复 | 视觉总览+对象编号+按需加载，AI 低 Token 全局审阅并修复 PPT | 百万字小说不失忆：正文+人物状态+时间线+伏笔图谱，事务式写作 |
| **解决的痛** | 上下文爆炸（`Context is too large`）——本项目构思过程中亲历 | AI 生成 Office 后无法验收；长文档审阅 Token 爆炸 | 长篇创作失忆、设定漂移、前后矛盾 |
| **目标用户** | 所有重度 Agent 用户（Claude Code/Codex/OpenClaw） | 企业办公、AI 生成物验收 | 网文作者、内容工作室 |
| **工程量** | ★★ 小：MCP + 抽取/提交/投影三件套，无渲染链路 | ★★★★ 大：Office 解析+渲染+视觉编号+diff 全链路 | ★★★ 中：无渲染链路，但图谱/时间线/连续性检查逻辑重 |
| **与 U-King 产品线协同** | ★★★★★ 直接增强 ClawX/U-Claw/Hermes 的长期记忆，装机即用 | ★★★ 可做 Open365 的验收模块 | ★★ 独立产品线 |
| **传播力/可演示性** | ★★★ 痛感强但演示不直观（要用几天才有感） | ★★★★★ 对比数据震撼（Token 省多少、多找出几个问题） | ★★★★ 故事性强、易传播 |
| **验证协议的完整度** | Memory 方言：验证 L2/L3 记忆 + 事务提交 | Office 方言：验证三层上下文 + 多渲染器共识 | Story 方言：验证状态/时间线/约束/事务全套 |
| **风险** | 与 Letta/各家原生 memory 功能撞车 | 依赖 OfficeCLI 等外部项目成熟度 | 市场付费意愿待验证 |

三条路径共享同一个协议核心（`.origin` 包 + 双向编译器 + 语义事务），**选哪条先走都不浪费**——差别只是第一个方言是 Memory、Office 还是 Story。

## 二、决策标准：ShadowBench

在选定 MVP 前，先做一个小规模公开基准，比较三种输入方式：

1. 原始纯文字 / Markdown
2. PDF 或普通截图
3. 本象包（atlas + graph + exact 三层）

**比较指标：**

```text
理解准确率 / 输入 Token / 响应时间 / API 成本
对象定位成功率 / 修改成功率 / 验证成功率 / 错误与幻觉率
```

**综合指标：**

```text
有效效率 = 正确完成任务数 ÷ (Token 成本 × 延迟)
```

**首批测试任务（对应三条路径各出题）：**

- 找出 100 页 PPT 中的重复页 / 文字与图表数据矛盾（路径②）
- 找出 Excel 中影响利润的公式依赖链（路径②）
- 中断会话后恢复项目状态，回答「上次我们决定了什么、还有什么没做」（路径①）
- 在 50 万字既有文本上续写一场戏，检查人物状态/伏笔/禁区违反数（路径③）

**决策规则：** 只有当本象包在任务上**明显**优于纯文本和普通截图（有效效率领先、且定位/验证成功率显著更高），对应路径才立项。如果不明显，协议假设本身需要修正——这比选错 MVP 更重要的信息。

### Phase 2：MVP 实现

按选定路径实现第一个方言的最小闭环（以路径①为例）：

```text
MCP 工具雏形：
  origin_save_state    # 本轮对话 → 候选状态变更 → 提交
  origin_load_state    # 新会话 → 恢复项目投影
  origin_query         # 按需取精确内容
```

- 接入 Claude Code / OpenClaw 实测
- 公开 Benchmark 数据与 Demo

## 五、首个对外 Demo 的口径（无论选哪条路径）

对外演示必须是**可对照的**：

> 普通方式用了多少 Token，本象方式用了多少；
> 普通方式找出几个问题，本象方式找出几个；
> 最后是否真的修改成功、能否出具证据。

先跑赢 Benchmark，「本象协议」才从抽象哲学变成事实标准。
