# xlsx 方言 —— 电子表格的本象

> 一张 Excel 表交给 AI，它看到的是 `cell[2,3]=1234`。
> 它不知道这个数是谁算出来的、依据什么、改了会牵动谁。
> 这份方言把表格导入本象包，让这三个问题都变成一条命令。

```bash
node adapters/xlsx/import.mjs adapters/xlsx/fixtures/B-缺陷.xlsx /tmp/B.origin
node compiler/cli.mjs diagnose /tmp/B.origin
#   → 自动抓出：公式列混入硬编码常量 / 同列公式形状不一致 / 求和漏行
#     / 错误值残留 / 引用不存在的表 / 文本型数字

node adapters/xlsx/import.mjs adapters/xlsx/fixtures/A-合规.xlsx /tmp/A.origin
node adapters/xlsx/trace.mjs /tmp/A.origin 预算!D7
#   → 这个数凭什么是这个数：顺依赖链追到人工录入的源头
```

---

## 为什么电子表格比图纸难

CAD 图纸是**静态**的：一根梁画在那里就是那里。
电子表格是**算出来**的：D5 的 50 不是谁填的，是 `B5-C5` 的结果，而 B5 又可能是别处算来的。

所以这份方言比 CAD 方言多做一件事：**建依赖图**。
而依赖图不需要给协议加任何东西——「谁依赖谁」本来就是本象六要素里的 `relations`。

## 对象模型

```text
book:<名>                工作簿
sheet:<表名>             工作表
header:<表>!<列>/1       表头（列的含义，不是数据）
cell:<表>!<列>/<行>      单元格
```

和 CAD 方言的 `ent:门窗/a1b2c3` 是同一个套路：**分类编进 ID**。
于是「D 列每一格都必须是公式」可以直接写成通配约束 `cell:预算!D/*`，
校验器不需要知道什么是电子表格。

两个设计细节，都是踩过坑之后定的：

- **`D/5` 而不是 `D5`**：通配是前缀匹配，`cell:预算!D*` 会把第 105 列的 `DA1` 一起匹上。
  列行之间加一道分隔符，列通配才是精确的。人读的 A1 地址保留在 `ref` 字段。
- **表头另立一类**：表头是列的**含义**，不是列里的一个数据点。
  混在一起的后果是实打实的——「D 列每格都必须是公式」会连标题「利润」一起判成缺陷，
  一张完全正常的表当场报两条错。

## 查什么

五条规则，全部对应有实证的真实事故（Panko 的综述：真实投产的表格约 1% 的格子含错，大表几乎必错）。

| 规则 | 抓什么 | 为什么肉眼看不出 |
|---|---|---|
| 公式列纯度 | 公式列里混进硬编码常量 | 有人为了对数把某格公式删了填死值，忘了改回来。这格从此不再随上游更新 |
| 同列公式一致 | 拖拽填充错了一格 / 插入行后公式没跟上 | `=B6-C5` 和 `=B6-C6` 长得几乎一样 |
| 求和覆盖 | `SUM(D2:D11)` 但数据已到 D12 | 新增的那行永远不进合计，总数一直是对的——只是少了一行 |
| 错误值残留 | `#REF!` / `#DIV/0!` 就摆在表里 | 照样被复制进报告 |
| 文本型数字 | 导出的「1,234」是字符串 | `SUM` 直接把它当 0，合计凭空少一截 |

**五条全部用协议既有的谓词表达（`in` / `not_equals`），没有为它们新增任何谓词。**

### 两处专门防假警报的设计

假警报比不查更糟——几次误报之后没人会再看体检结果。所以：

- **合计行单独放行**。`=SUM(D2:D6)` 与上面的 `=B6-C6` 形状天然不同。
  一视同仁地要求「同列形状一致」，会对着每一张带小计的正常表报错。
  判据是结构性的、不靠猜：对本列上方做纵向聚合的格子，就是小计格。
- **按列实际用法选规则集**（与 CAD 方言的 `numbering` 探测同理）。
  一列纯数据不会被套上「必须全是公式」。门槛定在 3——两格相同还可能是巧合。

### 共享公式必须翻译，否则会对好表报一列的错

Excel 存一列相同公式时不写十遍：第一格写全文并标 `t="shared" si="0" ref="D2:D11"`，
后面九格只写 `<f t="shared" si="0"/>`。

天真的解析器会认为后九格「没有公式」，于是「公式列混入硬编码常量」这条
**对着一份完全正常的表报九条错**。这份方言把主公式按行列偏移翻译给每个跟随格，
相对引用平移、绝对引用（带 `$`）不动——这正是 Excel 自己的语义，弄反了会把好表判成坏表。

## 依赖链：Excel 答不了的那个问题

```
$ node adapters/xlsx/trace.mjs /tmp/A.origin 预算!D7
预算!D7 = 270  ← =SUM(D2:D6)
├ 预算!D2 = 40  ← =B2-C2
│  ├ 预算!B2 = 100  （人工录入）
│  └ 预算!C2 = 60  （人工录入）
├ 预算!D3 = 50  ← =B3-C3
│  ...
这个数最终由 10 个人工录入的格子决定：预算!B2、预算!C2、…
```

Excel 有「追踪引用单元格」，但它只画一层箭头，只在打开那个文件时存在，
答不了「这个数当初是谁改的、依据什么」，也没法把整条链交给 AI。

本象包里这是**两条**持久的链，都可以被命令行问出来：

- `origin why <包> <对象.字段>` —— 历史链：谁、什么时候、依据什么改过
- `trace.mjs <包> <地址>` —— 依赖链：这个数由哪些数算出来

依赖链的**数据**用协议自带的 `relations` 存；把它渲染成人和 AI 读得懂的样子，
按 `decision:projector-per-domain` 是方言自己的事——协议统一的是事务与校验，
不是每个域该给模型看什么。

## 一源万影：影这一侧

导入只是半条路。整条回路闭合是这样的：

```bash
node adapters/xlsx/import.mjs  预算.xlsx        /tmp/A.origin   # 万源一象
node compiler/cli.mjs commit   /tmp/A.origin    tx.json --by 财务-张
node compiler/cli.mjs why      /tmp/A.origin    'cell:预算!C/5.value'
node adapters/xlsx/project.mjs /tmp/A.origin    /tmp/A-v2.xlsx  # 一源万影
```

实跑：

```
✓ 已落盘 seq 1–1，责任者 财务-张
cell:预算!C/5.value 当前值：82（经 1 次事务改动）
seq  at                        by       tx         from  to
1    2026-08-04T23:11:37.423Z  财务-张  fix-price  75    82

投影 42 个对象 → A-v2.xlsx（来源 seq 1）
⚠ 这是一份有损投影，以下信息没能带走：
   · 字段 formula_shape（13）——xlsx 装不下它
   · 1 条变更记录（证据链）——投影出去的值答不出「凭什么」，要追责请回到本象包
   · 4 个公式格的缓存值已过期——事务改了它们依赖的输入格，而本象不重算公式
```

**有了这一侧，「Excel 只是影子」才不是口号**——影子真的是从本象生成出来的。

### 往返保真：40/40 与 47/47 逐格一致

| 夹具 | 结果 |
|---|---|
| A-合规.xlsx | **40 格逐格一致**（种类 + 值 + 公式），0 差异 |
| B-缺陷.xlsx | **47 格逐格一致**，0 差异 |

其中一条值得单说：源文件里 D3–D6 是**共享公式**（只有 `si` 编号，没有公式文本），
投影写出的是显式 `=B3-C3`。**字节不同，语义相同**——往返比对认的是语义。

### 投影必须说清楚自己丢了什么

`xlsx` 装不下诊断结论（`hardcoded_in_block` / `range_gap` / `formula_shape`），
更装不下证据链。**有损不是问题，假装无损才是**——一份不声明自己丢了什么的投影，
会被下游当成本体使用，那正是本项目开篇要解决的「投影的投影」。

所以投影件默认多带一张**「投影披露」表**，把丢弃清单和来源 seq 写在里面，
跟着文件走，而不是留在生成它的那台机器上。同时 `projected` 事件入 provenance——
「这份发出去的报表是从哪个版本的世界生成的」，包里查得到。

### 缓存值过期：投影侧最容易出人命的地方

xlsx 的公式格存的是「公式 + 上次算出来的值」。事务把 `C5` 从 75 改成 82 之后，
`D5` 的公式还是 `=B5-C5`，但它存的值仍是按 75 算出来的 **55**（正确答案是 48）。

**Excel 打开时会重算，所以人看不见；可任何程序读这个文件，读到的就是 55。**

本象不重算——那需要一个完整的公式引擎（[decision:zero-deps](../../docs/07-开源与商业.md)，
而且那是 pycel 干的活）。但本象**手里有依赖图**，它知道哪些格子失效了。
知道而不说，就是在发一份自己知道有错的文件。所以投影顺着 `depends_on` 反向传播，
把受影响的公式格逐层找出来写进披露——实测 `C5` 一改，`D5`（直接）、
`E5`（隔一层）、`D7`（合计）全部被标出。

### 真实文件·第二轮（全盘扫描，含公式列的表）

于是扩大到 Documents / Desktop / D 盘：**210 份 .xlsx，271 万格**，
筛出 **51 份含公式列**（69.8 万格、205 个公式列）——公式类规则终于有考场了。

**第一轮跑出 1049 条 error，抽查发现绝大多数是假阳性。** 逐条判下来，
三个错误的建模假设被真实数据打掉：

| 打掉的假设 | 真实反例 | 修法 |
|---|---|---|
| 「公式列」= 整列都该是公式 | 「目录」表 D 列：`D2="生效时间"` 是表头但在**第 2 行**（第 1 行是合并大标题），`D3` 是被下面引用的源值 | 收窄成**公式块** = [本列第一个公式行, 最后一个非空行]，块之上的常量是标签和输入 |
| 块内任何常量都可疑 | 价格表大量用**分段小表**：一列里「51KG+」当段标题、下跟三行公式，重复十几段 | **只报数字，不报文字**——公式被填死时填进去的几乎总是数字 |
| 文本型数字总是缺陷 | 报价单「标签 + 数字」混排列里的 `"1"`：确实是文本型数字，但**没人对这列求和** | 只在该格真的落在某个聚合范围内时才报 |

| | 第一轮 | 收敛后 |
|---|---|---|
| error 总数 | 1049 | **164** |
| 零 error 的文件 | 12 / 51 | **39 / 51** |
| 公式列纯度 | 495 | **20** |
| 文本型数字 | 248 | **0** |
| 同列公式一致 | 162（error） | **降为 warning** —— 形状不同是嫌疑不是缺陷 |

**剩下的 164 条抽查均为真阳性**，例如某物流价格表「美国超大件」D 列：

```
D31 = C31-2.2    D32 = C32-1.3    D33 = 33.5   D34 = 33.5   D35 = 33.5
```

一列本该由 C 列算出来的价格，中间三行被填死成 33.5。是有意设的保底价还是漏改，
需要人看一眼——而在 Excel 里这三格和上面长得一模一样。

⚠️ 「抽查均为真阳性」是**抽查**，不是逐条复核 164 条；且判定人是写这些规则的同一个人。
准确的表述是：**假阳性从 1049 降到 164，且抽样未再发现假阳性**。

### 认得出的伪装

真实遇到的，不是假想的：

| 伪装 | 实际是什么 | 怎么办 |
|---|---|---|
| `.xlsx` 但开头是 `<html` | 业务系统「导出 Excel」导出的 HTML 表格。Excel 能打开，所以没人发现 | 里面没有单元格类型、数字全是字符串、公式一条都没有。另存为可拿到真格式，但公式救不回来——源头就没有 |
| `.xlsx` 但开头是 OLE2 魔数 | `.xls`（Excel 2003 二进制），和 xlsx 只是扩展名像 | 另存为 .xlsx |

## 先例：这件事别人做过

**「查电子表格公式缺陷」不是新方向，本方言不得声称是发明。**
详见 [表格与世界模型赛道调研](../../research/2026-08-表格与世界模型赛道调研.md)（2026-08-05 实查）。

最直接的先例是 **ExceLint**（`ExceLint/ExceLint-addin` 105★）：
*"Add-in for Excel that finds formula errors"*。
它和上面「同列公式形状不一致」那条是同一件事，**而且做得更细**——
它用信息论方法看**二维邻域**的异常，本方言只看同一列。

`pycel`（628★）也建公式依赖图，但目标是**重算**（把表格编译成 Python），
本方言的目标是**追责**（这个数由哪些人工录入决定、每一步凭什么）。

分界线不在检测能力上，在于结果去了哪里：

> ExceLint 出的是一份**报告**，读完就完了。
> 本象出的是一个**包**——检测结论落在对象字段上，能被约束校验、被事务修改、被 `why` 追责，
> 而且 AI 可以接着往下改，改错了当场退回。

同理，「表面保持二维、内部升维」也不是空白：Grist（11,414★）已经把它做完了。
本方言与那一类产品的差别是**不要求数据搬家**——原地读 xlsx，产出一个旁挂的包。

## 已知的边界

**单元格地址不是稳定 ID。** 在上面插一行，原来的 D5 就变成 D6——
xlsx 在「同一个东西改了值」和「东西还在原地但地址变了」之间无法区分。
这是格式本身的性质，不是导入器的缺陷。后果：跨版本对比会把「插了一行」
看成「从插入点往下每一格都变了」。退化写进包里（`book.id_basis=address`），`diagnose` 看得见。

**确定性检查抓不到的两类**（已写进 `selftest.mjs` 的 `DEFECTS` 目录并断言抓不到）：

- **整列用错了列**：本该乘税率却整列乘了折扣率。形状一致、无错误值、数值合法——
  需要知道这一列在业务上是什么意思。
- **数量级错误**：单价 10.00 填成 1000。值本身完全合法，只有懂这门生意的人看得出。

所以准确的表述是：**把电子表格的错误从「哪里都可能错」压到「错在语义那一类」，
剩下那一类交给人**——不是「AI 不会再算错」，是「错在哪一类现在是确定的」。
